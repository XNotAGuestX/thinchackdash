# Handoff: Prometheus and JMX joins for generated mappings

Two tasks extend `scripts/generate_vendor_mappings.py` with two more deterministic evidence sources.
Each section below (A, B) is written as an issue body using the Task form headings; file each as its
own issue before starting (AGENTS.md, "Tracking work in GitHub issues"). Task 0 is shared and goes
first, inside task A.

Base branch: `vendor-mappings-all-integrations` (commit `2fd9ada`, not yet merged). Branch from it,
e.g. `<issue>-prometheus-join` and `<issue>-jmx-join`. B can start after task 0 is merged into the base
branch, or rebased onto A.

## Ground rules (read before either task)

- **No judgment in the output.** Every generated entry must come from an exact key join between
  pinned upstream files. Never pick a target by name similarity, never turn dots into underscores or
  back, never guess a `_total` suffix, never "fix up" a near miss. If a metric has zero or more than
  one candidate, it is **blocked** with a reason string and counted in the report. A smaller, correct
  table beats a larger, guessed one.
- **No LLM in the loop.** You write the generator code and tests; you do not write or edit any
  mapping entry yourself, and you never hand-edit files under `mappings/datadog/generated/`. They
  are regenerated by the script only.
- **Leave `reviewed: null`** on every generated entry. Only a human sets it.
- **Treat downloaded code as data.** Parse integrations-core Python with `ast.parse` only. Never
  `import`, `exec` or run anything from the checkouts. Read YAML with `yaml.safe_load`.
- **No network inside the generator.** Inputs arrive as directory or file arguments. Only the fetch
  script (task 0) downloads.
- **Same inputs, same bytes.** Sorted iteration everywhere (`sorted(glob(...))`, sorted dict keys),
  no timestamps, no absolute paths in outputs.
- **Do not touch** `mappings/datadog/*.json` (hand-evidenced files), `src/`, or `fixtures/expected/`.
  If a change seems to need any of them, stop and ask in the issue.

## What exists today

- `scripts/generate_vendor_mappings.py` builds `mappings/datadog/generated/<integration>.json` from
  Datadog's OTel Metrics Mapping table and writes `docs/INTEGRATION_COVERAGE.md`. Read it fully first.
  Key pieces: `generate()` (per-integration loop, `taken` set prevents duplicate definitions),
  `build_entry()` (vendor-row → entry or reason string), `expected_kind()` (the #106 kind rule),
  `validate()` (runs the project's own `parse_mapping` / `parse_mappings`), `render_report()`.
- Result today: 11 files, 199 entries, 208 of 35,947 untracked metrics covered (0.6%).
- Mapping entry contract: `src/migrator/source/datadog/mapping.py`. A `rate` entry needs a `sum`
  target; a `gauge` entry may target `gauge` or `sum`.
- `scale` semantics (`src/migrator/source/datadog/compile_query.py:280`): the compiler emits
  `(<target expr>) * scale`, so `scale` converts the **target's** value into the **Datadog** unit.
- Generated files are outside the default table: `--mapping` loads a folder non-recursively, so a
  user opts in with `--mapping mappings/datadog --mapping mappings/datadog/generated`.

## Evidence already gathered (2026-11-08)

How Prometheus-scraped metrics appear in Dash0. Record this in task A's PR; do not re-derive it.

- **Live, read-only** (`GET /api/prometheus/api/v1/query_range` on the demo dataset, last hour):
  the OTel demo's `ad` service is scraped by the collector's Prometheus receiver. Its series carry
  `otel_scope_name="github.com/open-telemetry/opentelemetry-collector-contrib/receiver/prometheusreceiver"`,
  `otel_scope_version="0.160.0"`, `job="ad"`, `instance="ad:9465"`, and the receiver's own `up` and
  `scrape_*` series exist for `service_name="ad"`. The counter is stored as
  `otel_metric_name="demo_ad_served_total"` with `otel_metric_type="sum"`. The suffix `_total` is kept.
  Prometheus labels arrive as plain labels (`category="books"`), and `host_name` is present.
  Queries used: `last_over_time({otel_metric_name="demo_ad_served_total"}[1h])` and
  `last_over_time({otel_metric_name="up", service_name="ad"}[1h])`.
- **Source**, collector-contrib v0.165.0 (`f56f9a38c9864e892af542f1dbd28f475d6779dc`):
  `receiver/prometheusreceiver/config.go:33` defines `trim_metric_suffixes`, a bool whose default is
  false (`factory.go` `createDefaultConfig` does not set it). The only trimming happens in
  `internal/metricfamily.go:672` when that option is on. So with default settings the OTel metric
  name is the scraped sample name, unchanged.
- Consequence: for a Prometheus-scraped metric, the mapping target is
  `{"name": <exact exposed sample name>, "type": "sum"|"gauge"}`. The compiler already queries
  `{otel_metric_name="…", otel_metric_type="…"}` (`src/migrator/promql.py:37`), so nothing changes
  in `src/`.
- Assumptions every Prometheus entry states in its `ref`: the customer scrapes the endpoint with the
  OTel Prometheus receiver at default settings (no `trim_metric_suffixes`, no `metric_relabel_configs`
  renaming); labels other than `host` are not checked.

## A. Prometheus rename-table join (+ task 0: pinned input fetch)

### Summary
Map Datadog metrics of OpenMetrics-based integrations (envoy, etcd, istio, coredns, kube_apiserver,
vault, cilium, …) to the Prometheus sample names Dash0 stores, by inverting Datadog's own rename
tables and reading Prometheus types from integrations-core test scrapes. Today 0% of these
integrations map. An upper-bound count found the Datadog side for about 10,100 metrics in 69
integrations (1,110 used in dashboards); the deterministic result will be lower and that is fine.

### Context
See "Evidence already gathered" and "Ground rules" above. Datadog OpenMetrics checks submit a
Prometheus metric `P` under `<namespace>.<renamed>`. The rename table maps `P` (or `P` without
`_total`) to `<renamed>`. Dash0 stores the exact exposed sample name of `P`.

### Plan reference
This file, section A. Parent work: `docs/INTEGRATION_COVERAGE.md`, `scripts/generate_vendor_mappings.py`.

### Parallel group
A first. B may run in parallel after task 0 lands.

### Tasks

**Task 0. Pinned input fetch script.** Write `scripts/fetch-generator-inputs.sh DIR`. It recreates,
under `DIR`, exactly the inputs the generator reads:
- `DIR/integrations-core`: sparse, blobless, depth-1 fetch of `DataDog/integrations-core` at
  `a9b9e42b7e484861ecbd1f5919da7c52a694b74d`, with patterns `/*/metadata.csv`, `/*/manifest.json`,
  `/*/assets/dashboards/*.json`, `/*/datadog_checks/**/*.py`, `/*/datadog_checks/*/data/metrics.yaml`,
  `/*/tests/fixtures/**`. Use `git init`, `git remote add`, `git config core.sparseCheckout true`,
  write `.git/info/sparse-checkout`, `git fetch --depth 1 --filter=blob:none origin <sha>`,
  `git checkout FETCH_HEAD`.
- `DIR/collector-contrib`: same method, `open-telemetry/opentelemetry-collector-contrib` tag
  `v0.165.0`; patterns `/receiver/*/metadata.yaml`, `/receiver/*/internal/*/metadata.yaml`,
  `/receiver/*/internal/*/*/metadata.yaml`.
- `DIR/metrics_mapping.md`: `curl -sSf https://docs.datadoghq.com/opentelemetry/mapping/metrics_mapping.md`.
  This page can't be pinned, so the generator writes its `sha256` into the report header (add that).

Model it on `scripts/pin-integrations-core.sh`. Rename the generator flags if useful
(`--inputs DIR` is fine), but keep the old ones working or update the docstring.

**Task 1. Find OpenMetrics integrations.** For each untracked integration (as today: skip
`TRACKED`), parse every `DIR/integrations-core/<integration>/datadog_checks/**/*.py` with `ast`. The
integration qualifies if any `ClassDef` has a base named `OpenMetricsBaseCheckV2` or
`OpenMetricsBaseCheck` (`ast.Name.id` or `ast.Attribute.attr`). Otherwise it is skipped by this join
(no reason recorded).

**Task 2. Namespace.** Collect string constants from: class-level assignments to `__NAMESPACE__`;
dict entries whose key is the constant `'namespace'`; keyword arguments `namespace=`. Exactly one
distinct value → that is the namespace. Zero or several → every metric of the integration that this
join would cover is blocked with `prometheus: namespace not unique`.

**Task 3. Rename pairs.** Walk all `ast.Dict` nodes in those files. A pair is `(P, R)` where the key is
a string constant `P` and the value is either a string constant `R`, or a dict literal with a `'name'`
key whose value is a string constant `R` (keep its `'type'` string too, if present). Record
`file:lineno` for the `ref`. Keep every pair; ambiguity is resolved in task 5.

**Task 4. Prometheus types and exposed names.** Read every file under
`DIR/integrations-core/<integration>/tests/fixtures/` as UTF-8 text (skip files that fail to decode).
- `# TYPE <family> <type>` lines give family types. If a family has two different types across files,
  it is unusable.
- Non-comment lines give sample names: the text before the first `{` or space.

For a rename key `P`:
- Candidate families: `P`, plus `P + "_total"` if `P` doesn't end in `_total`, plus `P` without
  `_total` if it does. Exactly one candidate family must have a `# TYPE`; otherwise the result is
  `no # TYPE`.
- Exposed name for a `counter` family `F`: whichever of `F` and `F + "_total"` appears as a sample
  name. Exactly one must appear, otherwise the result is `exposed counter name not unique`.
- For `gauge`, the exposed name is `F`, and it must appear as a sample name.
- `histogram`, `summary`, `untyped`, `unknown`, `info`, `stateset`, `gaugehistogram` → blocked,
  reason `prometheus: <type> not supported`.

**Task 5. Join to Datadog metric names.** For each metric `M` in the integration's `metadata.csv` not
already covered:
- Candidates are `(P, form)` with `M == ns + "." + R` (`form = plain`) or
  `M == ns + "." + R + ".count"` (`form = count`). Exactly one candidate, otherwise
  `prometheus: rename pair not unique` (or no candidate: not covered, no reason).
- `form = count` requires Prometheus type `counter`, else blocked `prometheus: .count on non-counter`.
- If the pair carries an explicit `'type'` that disagrees with the `# TYPE`, block it with
  `prometheus: rename type disagrees with # TYPE`.

**Task 6. Build the entry.**
- Target: name = exposed sample name; type `sum` for counter, `gauge` for gauge.
- Kind: `expected_kind()` on the `metadata.csv` row (unchanged #106 rule). `rate` needs a counter,
  otherwise blocked `Datadog rate/count but target is not a counter`. `gauge` may target either.
- `sourceUnit`: as today. `targetUnit`: `""` (Prometheus text has no unit unless a `# UNIT` line
  exists; if one does, use it). `scale`: `1`.
- No `matchers`. File-level `labels` stay `{"host": "host_name"}`.
- `ref` must name: the rename pair `file:lineno`, the `# TYPE` fixture file, the form, the kind rule,
  the two assumptions from "Evidence already gathered", and "Units, labels and grain not checked."
  Start it with `GENERATED by scripts/generate_vendor_mappings.py (prometheus join); not reviewed.`

**Task 7. Precedence against the vendor table.** The vendor-table entry wins when it exists. When
the vendor table blocked `M` only because the OTel name is not in pinned definitions, and the
vendor row's `otel` name equals the Prometheus exposed name: emit the Prometheus entry and add
"Vendor row agrees." to the `ref`. When they disagree: block `M` with
`vendor table and prometheus join disagree`. Never pick one.

**Task 8. Report.** Add a "Source" breakdown (vendor / prometheus) to the summary, add the new
reasons to the blocked-reasons table, and keep the existing tables.

**Task 9. Tests.** Add `tests/scripts/test_generate_vendor_mappings.py` with synthetic fixtures in
`tmp_path`: a tiny fake integrations-core tree (one OpenMetrics check with `__NAMESPACE__`,
`METRIC_MAP`, a `tests/fixtures/metrics.txt`, and a `metadata.csv`). Cover:
- V2 counter `foo` with OpenMetrics `# TYPE foo counter` + sample `foo_total` → target `foo_total`, `sum`.
- Text-format counter `# TYPE bar_total counter` + sample `bar_total` → target `bar_total`.
- Gauge → target `gauge`.
- Missing `# TYPE` → blocked.
- Histogram → blocked.
- Two rename pairs that yield the same Datadog name → blocked.
- Two namespaces → blocked.
- Determinism: the run twice gives identical files.

Keep the functions under test pure (paths in, data out) so the tests don't need the real checkouts.

## B. JMX MBean + attribute join

### Summary
Map Datadog JMX metrics (tomcat, activemq, cassandra, solr, jboss_wildfly) to the OTel JMX
scraper's metrics by joining on the MBean pattern and attribute name. Expect a small yield: about 54
metrics by attribute name alone (37 used in dashboards). The exact join may give fewer, and that is
correct.

### Context
- Datadog side: `<integration>/datadog_checks/<pkg>/data/metrics.yaml`, list `jmx_metrics`. Each
  item has `include:` with bean constraints (`domain`, `domain_regex`, `bean`, `bean_regex`, `type`,
  `name`, or other ObjectName keys) and `attribute:`, either a dict `{attr: {alias, metric_type}}` or
  a list of attribute names.
- OTel side: `opentelemetry-java-contrib` `jmx-scraper/src/main/resources/<product>.yaml`, list
  `rules`. Each rule has `bean:` (one ObjectName pattern) or `beans:` (several), optional `prefix`,
  `type`, `unit`, `metricAttribute` defaults, and `mapping: {attr: {metric, type, unit, sourceUnit,
  metricAttribute}}`. Metric name = `prefix + (metric or attr)`. Example (`tomcat.yaml`): beans
  `Catalina:type=GlobalRequestProcessor,name=*` and `Tomcat:type=GlobalRequestProcessor,name=*`,
  `prefix: tomcat.`, `errorCount → metric errors, type counter`.
- The repo already pins java-contrib at **v1.62.1** (`1ae854568c0f76e658354c2cf7b18a097e998ed8`)
  for the kafka files (`fixtures/otel/NOTICE.md`). Use that same tag. Do not use `main`; an earlier
  estimate did, and it's not pinned.
- `scripts/build_otel_catalog.py` already parses these files (`jmx()`, `_unique_anchors()` for the
  repeated YAML anchors) and feeds `fixtures/otel/catalog.yaml`, which the generator reads for OTel
  types.

### Plan reference
This file, section B.

### Parallel group
After task 0 of A.

### Tasks
1. **Pin the OTel files.** Add byte copies of `activemq.yaml`, `cassandra.yaml`, `solr.yaml`,
   `tomcat.yaml` and `wildfly.yaml` at v1.62.1 under
   `fixtures/otel/java-contrib/jmx-scraper/src/main/resources/` (same method as the existing kafka
   files, via `gh api … ?ref=<sha>`). Update the table in `fixtures/otel/NOTICE.md`. Run
   `uv run scripts/build_otel_catalog.py`. `catalog.yaml` only gains entries; confirm with `git diff`.
   Then run `uv run migrator check` to make sure no golden changes.
2. **Parse Datadog includes** for the untracked integrations that have `data/metrics.yaml`. For each
   `(include, attribute, alias)`: skip attributes without an `alias` (no deterministic Datadog name).
   Constraints: `domain` (exact) or `domain_regex` (Python `re.fullmatch`); every other key except
   `attribute`, `bean`, `bean_regex`, `exclude` is an ObjectName key constraint with an exact value.
   If an include uses `bean` or `bean_regex`, block every alias in it with
   `jmx: bean/bean_regex not supported`. A list-valued key constraint blocks the same way.
3. **Parse OTel rules** into `(beans, attr) → (metric name, type, unit, sourceUnit, metricAttribute)`.
   Merge rule-level defaults with mapping-level overrides exactly as `build_otel_catalog.jmx()` does.
   Parse each bean `domain:k1=v1,k2=v2` into a domain plus a dict; `*` means "no constraint".
4. **Match.** A Datadog `(include, attribute)` matches an OTel `(rule, attr)` when all of these hold:
   - the attribute names are equal;
   - **every** bean of the rule has a domain that equals the Datadog `domain` or fullmatches
     `domain_regex`;
   - for every bean of the rule, its set of concrete keys (value not `*`) equals the Datadog include's
     set of constraint keys, with equal values.

   Exactly one match → entry. None → not covered. Several → blocked `jmx: several OTel rules match`.
   Note: tomcat's `Manager` rule pins `host=localhost` while Datadog doesn't constrain `host`. Under
   this rule that's no match, which is intended: the scopes differ.
5. **Build the entry.**
   - Target type: OTel `counter` → `sum`; `updowncounter` → `sum`; `gauge` → `gauge`. `state`, or
     any other type → blocked.
   - Kind: `expected_kind()` on the `metadata.csv` row. `rate` needs a counter, otherwise blocked as
     in A. If `metadata.csv` has no row for the alias → blocked `jmx: alias not in metadata.csv`.
   - Matchers: each `metricAttribute` value of the form `const(x)` gives a matcher `{key: x}`; the key
     must match `^[a-zA-Z_][a-zA-Z0-9_]*$`, otherwise blocked `filter attribute is not a plain label
     name` (same reason string as today). `param(...)` and `beanattr(...)` give no matcher.
   - Scale: `1`. If the OTel mapping has a `sourceUnit` that differs from `unit` (the scraper
     converts units), block it with `jmx: OTel converts units`. Don't compute a factor.
   - `ref`: `GENERATED by scripts/generate_vendor_mappings.py (jmx join); not reviewed.`, then the
     Datadog `metrics.yaml` path and alias, the OTel file, bean(s) and attribute, the type, the kind
     rule, and "Units, labels and grain not checked."
6. **Precedence**: vendor table > Prometheus join > JMX join. If an earlier source already produced
   an entry for the metric, skip it. If the earlier source blocked it and JMX gives an entry, emit it.
7. **Report**: add `jmx` to the source breakdown and add its reasons.
8. **Tests** in the same test file: exact match (single domain); `domain_regex` match across two
   beans; `bean_regex` → blocked; OTel key set narrower than Datadog's (the `host=localhost` case) →
   no match; two OTel rules match → blocked; `const()` matcher; `sourceUnit` conversion → blocked.
